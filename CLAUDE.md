# CLAUDE.md

## Project

**Focus Screen**: an Electron desktop app for macOS and Windows that shows music, a combined to-do list, and a timer on an external monitor. Read `project_brief.md` for the full spec, milestones, and acceptance criteria before starting any milestone.

Desktop only. Never add mobile, React Native, Capacitor, or responsive-for-phone work.

## Stack

- Electron + TypeScript (strict), scaffolded with electron-vite, React in the renderer
- Two windows load the same renderer page: the Focus Screen (`#focus`) and Customize (`#customize`), a normal window on the main screen so changes show live on the Focus Screen (the user chose this over the mockup's in-place screen). Main pushes state to both; only the Focus Screen plays the chime.
- Plain CSS with CSS variables for theming (no Tailwind, no UI kit)
- Native helpers in `native/`: Swift CLI (macOS Reminders), C# console app (Windows media controls). They print one JSON object per line to stdout.
- The Reminders helper is wrapped in a tiny `Focus Screen Reminders.app` and asks macOS for Reminders access as itself (it re-launches itself "disclaimed"), because under `npm run dev` the terminal app would otherwise be asked. It takes JSON-line requests on stdin and exits when stdin closes. The same app has a calendar mode (`--calendar`, run as its own process) for Next class in the top bar: it only reads timed events from the calendars picked as class calendars, from today through a week on (8 days: the end-of-day swipe reaches the next day with classes; capped at 8 × 24 h, the helper's limit). A third mode, `--map '<json>'`, makes one Apple Maps picture (MapKit snapshot, dark or light, tilted) of a class building and exits, and a fourth, `--route-map '<json>'`, one flat picture of a box around a bus's path for the Next bus route card (the app draws the path on it, lined up by where the box's corners landed); neither reads anything on the Mac. A fifth, `--haptics` (approved by the user on 2026-10-26), plays the Force Touch trackpad's alignment tick (`NSHapticFeedbackManager`) for each "tick" line on its stdin, and the firmer level-change one for "tick firm" (a wheel that came onto 0 at 0.7 px/ms or more: the user found the light tick hard to feel at speed): main starts it as the Timer card's length wheels open and stops it after a minute of quiet (`services/timer/haptics.ts`); it reads nothing and needs no access. A sixth, `--location` (approved by the user on 2026-10-27, for the weather pill), runs as its own disclaimed process like calendar mode, so macOS asks for Location as "Focus Screen Reminders": it reports Location access, gives one fix per request (nothing keeps running between), and looks up the town at a position it's given (MapKit's reverse geocoding, Apple); main starts it while weather is on, and for trips as the Privacy section says; both share the one helper process (`services/weather/sharedLocation.ts`, ref-counted, so it stops when neither needs it) (`services/weather/location.ts`). A seventh, `--places` (approved by the user on 2026-11-02, for the trip planner's "anywhere" search), is Apple's place search (MapKit `MKLocalSearch`, `Places.swift`) given only the typed text and a fixed Phoenix-area box that's the same for everyone; it is long-running while the trip card is open, stopped after 60 s without a search, never disclaimed (so it can never run under the weather pill's Location grant), and reads nothing on the Mac (`services/trips/placesHelper.ts`, `applePlaces.ts`). The trip search is a RAPTOR search written by OpenAI's Codex against Claude's contract tests (`collab/trip-planner/`, the user asked to build it together), running in an Electron utility process like the dictionary romaji's (`services/trips/worker.ts`, started by `client.ts`, stopped after 2 min idle so the timetable's memory goes back) over a timetable made from the same schedule download as Next bus's stop list; live Trip Updates are applied per run. AppKit counts a snapshot's y up from the bottom: both modes turn it into y down before printing. Dev runs the copy in `~/Library/Developer/FocusScreen` (outside ~/Desktop, so it never needs Desktop-folder access), and packaging copies that same build into the app (`scripts/after-pack.mjs`).
- Auto-sync lyrics (macOS): `Focus Screen Audio.app` (`native/mac-audio`, Swift) records only the music player's audio through a Core Audio process tap, and asks for "System Audio Recording" as itself, disclaimed like the Reminders helper. A Python worker (`native/aligner/aligner.py`) lines plain lyrics (LRCLIB's, or VocaDB's when LRCLIB hasn't got the song) up with the recording on the Mac's GPU. English and Japanese songs go through CTC forced alignment with local wav2vec2 models (`native/aligner/ctc.py`: wav2vec2-large-960h-lv60-self, reazon japanese-wav2vec2-base-rs35kh), about 2–6 s a song with word timings. Other languages, unknown ones (romaji) and songs the CTC pass can't place fall back to Whisper large-v3-turbo through stable-ts. Measured on 25 recordings with LRCLIB answer keys on 2026-10-19: 65% of lines within 0.5 s and 83% within 1 s, against Whisper's 60% and 77%, in a quarter of the time. Its runtime (~4 GB: venv + models) lives in `userData/aligner`, installed by `npm run setup:aligner`, never shipped in the app. It only runs for songs that have words but no timings, and the Customize switch is off by default. "Prepare playlist" (Customize › Music, `services/autosync/prepare.ts`) plays a YouTube Music playlist muted so those songs get timed before they're listened to: a second audio helper holds a muted tap on the browser (the helper's `mute` op; a muted tap only silences while it's read, so its audio is read and thrown away), songs that need timing play to the end, the rest are skipped with the extension's `next`, and the run ends at the playlist's end (its `list` changes), on Stop, or on its safety limits. The whole browser goes quiet (Safari's own tab mute cuts the sound before a tap can hear it), so "Prepare while I'm away" (`services/autosync/away.ts`, setting `music.prepareWhenAway`, off by default) only runs it while nobody uses the Mac: after 5 min without input (`powerMonitor.getSystemIdleTime`), with a playlist on in YouTube Music, playing or paused (the user chose that idle means away even while music plays; a paused one also needs the browser quiet, so a video in another tab isn't muted), and it stops the moment there's input again. Dev builds take `FOCUS_SCREEN_AWAY_AFTER_SEC` to shorten the wait.
- Moving cover parts (macOS): a Python worker (`native/cover-motion/worker.py`) cuts parts out of the playing cover with SAM 2.1 (`facebook/sam2.1-hiera-base-plus`, Apache-2.0, through transformers on MPS) from the user's clicks in Customize, and builds each part's weight map (R motion, G how far from its pin, B its feathered mask), its spray emitters and a plate (what's under bobbing parts, filled in). Main keeps a recipe per cover, keyed by a perceptual hash (`coverKey`, so the queue's small copy matches), in `userData/cover-motion/library/<key>/`, and the editor works in a `draft/` copy so closing without saving never touches what's saved. The renderer draws it live in WebGL (`widgets/music/coverParts`). Its runtime (~1.1 GB: venv + SAM) lives in `userData/cover-motion`, installed by `npm run setup:covers`, never shipped (only `worker.py` is). Automatic part-finding (phase 2 of `docs/superpowers/specs/2026-10-21-layered-animated-cover-design.md`) was trialled on 2026-10-22 and shelved by the user: a local Qwen3-VL-8B plus Grounding DINO moved 5 of their 10 covers well, for ~6 GB more download and ~7.5 GB of memory a song; the clicks were made accurate instead.
- Romaji made on this computer (any platform, `services/lyrics/madeRomaji/`; approved by the user on 2026-10-23, after the search for another free romaji source found none whose terms allow it): for the lines VocaDB has no romaji for, and songs it hasn't got, a dictionary reads the Japanese lyrics already shown. kuromoji 0.1.2 (Apache-2.0, IPADIC; its dictionary ~17 MB, shipped) splits a line into words with readings; our own kana table (`kana.ts`, Hepburn as VocaDB writes it: ou, uu, っち "cch", を "o") spells them, not wanakana, which spells loanword sounds apart (ヴァ "vua", ディ "dei"). `readings.ts` fixes what a dictionary of written Japanese gets wrong in songs: particles (は wa, へ e, を o), っ and ー across words, readings in brackets after a kanji (運命(さだめ)), numbers with counters (一人 hitori, 一歩 ippo, 三千 sanzen), and lyric readings (何の nan no, 良い ii, 君, 側 soba after a pronoun, 空回り kara, 征く yuku, 々). `learn.ts` learns readings from the user's own saved VocaDB romaji (a reading at least two songs use, 60% of the time, only from lines the swap makes exactly right; a song saved twice counts once), kept in `lyrics-romaji-learned.json` and learned again only once more VocaDB romaji is saved (pairing all songs takes ~5 s), after the song at hand. Measured on the user's 183 songs VocaDB has romanized (7,501 lines, never tuned on): 87% of lines exactly as VocaDB writes them, against 69% from the dictionary word by word, and 87.75% with learning (each song left out); of what's left, about half is VocaDB's own text differing and a third the singer's reading (明日 asu, 永遠 towa). kuromoji holds ~400 MB once loaded, so it runs in an Electron utility process (`worker.ts`, started by `client.ts`) that's stopped after 60 s idle, giving all of it back; each song's romaji is saved (`lyrics-romaji-made/`), so the dictionary loads once per song. The idea of picking the singer's reading by scoring candidates against the recording (auto-sync's Japanese CTC model) needs recording songs that don't need timing, which the privacy rules below don't allow; not built.
- Color-Code Lyrics window (singer colors, macOS for the waveform; the user's own idea, 2026-11-02, "in a whole different tab, not customize tab"): a third window, `#lyrics-editor`, a normal window on the main screen like Customize ("Color-Code Lyrics…" in the Music menus, off while nothing plays or the song has no lyrics), so the Focus Screen shows the coding live as it's made. Its waveform has its own audio helper process (`singers/tap.ts`: the auto-sync helper app, a tap on the player's processes only, never auto-sync's own recording) opened with the window and closed with it; it needs the helper, not the Python aligner, so it works without auto-sync's add-on, all but Time by listening, which uses the add-on's aligner in a worker of its own (stopped 3 minutes after its last run or when the window closes); and without recording access the editor works with no waveform and says so. Nothing new is installed or downloaded.
- Browser extension in `extension/` (MV3, TypeScript, built with Vite) for YouTube Music in Chrome and Safari. Safari wraps the same code (built to `dist-safari/` with a non-persistent background page, since Safari's service-worker background never answered) in an Xcode container app at `native/safari-extension/`.
- electron-builder for packaging. Only `out/`, `package.json` and production deps ship (an allowlist, so a stray file like a downloaded OAuth client JSON never does). Fuses turn off run-as-Node so nothing can borrow the app's Automation/Reminders permissions. Signed with the Apple Development certificate, not notarized. The Mac build goes to `~/Library/Developer/FocusScreen/dist`, because ~/Desktop syncs to iCloud, whose Finder attributes break codesign.

## Commands

```bash
npm install
npm run dev          # run the app with hot reload
npm run typecheck    # must pass before a task is done
npm run lint
npm test             # unit tests (Vitest); npm run test:watch while developing
npm run format       # Prettier (ignores CLAUDE.md, project_brief.md, design/)
npm run build:mac    # signed .dmg → ~/Library/Developer/FocusScreen/dist (builds the Reminders helper first)
npm run install:mac  # build:mac, then quit the installed app, keep the last 2 installs in ~/Library/Developer/FocusScreen/previous, install to /Applications and open it (--skip-build installs the last build)
npm run build:win    # package Windows installer
npm run build:extension  # browser extension → extension/dist (Chrome: Load unpacked) + extension/dist-safari
npm run build:safari     # extension + Safari container app (Xcode), installed to ~/Applications
npm run build:reminders  # Reminders + Calendar helper (Swift) → ~/Library/Developer/FocusScreen; rerun after changing native/mac-reminders
npm run build:icons  # redraw the app + menu bar icons from scripts/build-icons.mjs → build/, assets/tray/
npm run build:audio  # audio helper (Swift) → ~/Library/Developer/FocusScreen; rerun after changing native/mac-audio
npm run setup:aligner  # auto-sync's Python runtime + CTC and Whisper models (~3.3 GB download) → userData/aligner
npm run setup:covers   # moving cover parts' Python runtime + SAM 2.1 (~1.1 GB) → userData/cover-motion
```

Settings live in `~/Library/Application Support/Focus Screen/settings.json` (macOS) or `%APPDATA%\Focus Screen\settings.json` (Windows); the running timer is saved next to it in `timer.json`, the chosen background photo (a re-encoded copy, never the original) in `background.jpg`, lyrics are cached one file per song in `lyrics/`, per-song lyrics timing fixes are in `lyrics-offsets.json` and the user's own lyrics picks ("Pick Other Lyrics…": a version's LRCLIB id, time by listening, or none) in `lyrics-picks.json` (both find a song saved a second longer or shorter, `nearSongKeys`: players report the same song's length a second apart from play to play), auto-synced line timings in `lyrics-autosync/` (keyed by song and the plain text they were made for), VocaDB's romaji for Japanese songs in `lyrics-romaji/`, romaji made from the dictionary in `lyrics-romaji-made/` (per song and the lines it was made for, `MADE_ROMAJI_REVISION`) and the readings learned from VocaDB's in `lyrics-romaji-learned.json`, the user's singer colors in `lyrics-singers/` (one JSON per song, with the lines the user added to it, named by a hash of the song's key, found a second longer or shorter too; `waveforms/` the song's loudness outline only, one peak per 20 ms, nothing that can be played back; `pictures/` the user's own badge pictures as re-encoded 256 px PNGs, with `index.json` for singers they added), the aligner runtime in `aligner/`, the moving cover parts' runtime in `cover-motion/` (`.venv`, `models/`) and each cover's parts in `cover-motion/library/<key>/` (recipe, built numbers, masks, weight maps, plate), ASU's building list (Next class map) in `asu-buildings.json` (refreshed monthly) and each class building's map picture in `class-maps/`, other schools' building maps from OpenStreetMap in `school-maps/` (one file per school), Next bus's stop list (Valley Metro's stops with their positions, the routes and headsigns at each, and each route's path, simplified, with each stop's place along it worked out from the order trips make their stops, so a street a route runs down twice gets each stop on its own pass, and a stop a trip makes twice (an Orbit's first and last at Tempe TC) keeps each visit's place, picked by the arrival's stop_sequence; made from its schedule; lists saved before paths or places existed (`STOP_LIST_REVISION`) are downloaded again once) in `transit-stops.json` (with the trip timetable beside it, `transit-timetable.bin`, ~8.5 MB, made from the same download; a stop list saved before it, `STOP_LIST_REVISION` 4, is downloaded again once) and the route card's map pictures in `transit-maps/`, Home, saved places and the last ten recent destinations of the trip planner in `trip-places.json`, check-offs made while Canvas is connected through its read-only calendar feed are in `canvas-feed-done.json`, and the user's own homework and exams (the Homework to-do source) in `homework.json` (only what's still to do: a ticked homework leaves it the moment it's ticked, an exam once it's over). The weather saves nothing: where the Mac is, its town and the forecast stay in main's memory. The mockups are in `design/` (open the `*.dc.html` files over a local server).

Version pins: electron-vite 5 needs Vite 7, and typescript-eslint needs TypeScript < 6.1, so don't bump Vite to 8 or TypeScript to 6+ until those catch up.

## Architecture rules

- `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true` in the renderer. The renderer never touches Node, the file system, or the network directly.
- All IPC channels and their payload types are defined once in `src/main/ipc.ts` and reused by preload and renderer. No stringly-typed channels scattered around.
- Every external source goes behind an interface (`MusicAdapter`, `TodoProvider`). The UI only sees the shared types (`Track`, `PlaybackState`, `TodoItem`, `TimerState`).
- Every adapter and provider has a `mock` version. `npm run dev` with no accounts connected must still show a full, realistic screen.
- Platform-specific code checks `process.platform` in one place (the adapter factory). Unsupported sources hide in the UI and never crash.
- Native helpers are spawned by the main process; restart them if they exit and treat malformed output as "no data", never as a crash.

## Security and privacy (non-negotiable)

- Tokens and refresh tokens only go through `services/secrets` (Electron `safeStorage`). Never write them to settings JSON, logs, or the console.
- Never commit secrets, `.env` files, OAuth client secrets, or real Canvas data. Keep `.gitignore` covering them.
- Canvas data is the user's own academic data: it only goes to the local UI and back to Canvas. Never send it to any other service.
- Calendar events (Next class) are read only from the calendars the user picks, never written, and only go from the helper (Apple Calendar) or Google Calendar's API to the screen. Never log their titles. A class's location is matched to an ASU building on this Mac; only that building's position (from ASU's own list) is ever sent anywhere, to draw its map.
- The user's own homework and exams (the Homework to-do source) are saved only in `homework.json` on this Mac, never sent anywhere, never logged (titles and classes stay out of logs and error messages). The class picked for one is a class-calendar event's title, saved with it: a new place calendar titles live, approved by the user on 2026-10-27 on condition that a ticked homework is deleted for good an hour after, class name and all. Asked whether that holds while the app isn't running, they took the strict way: a tick removes it from the file at once, it stays on screen as done for the hour from memory only, unticking saves it back, and a quit within the hour means it's gone. An exam leaves the file once it's over (at the next launch if it ended while the app was closed).
- The only third-party requests allowed besides Canvas and Google are LRCLIB, with song metadata only, plus the words the user types in "Pick Other Lyrics…" › "Search with other words…", and a picked version fetched again by its id; ## Code style

- TypeScript strict, no `any` (use `unknown` + narrowing). Small files, named exports.
- React function components and hooks. Widget state comes from main-process services via IPC subscriptions, not from polling inside components.
- Times are handled in seconds (numbers) internally; format only at display time.
- Comments explain *why*, not *what*.

A second voice (a backing line, an echo) is its own row, a little smaller, directly under its main line's romaji, lit on its own timing, with no pop or swell; two rows can be lit at once and the window opens a row's height for it. Romaji takes its line's colors, cut where the singers change by sounds (morae, never letters; `romajiCuts`): sure only within one mora, else a gradient of the line's singers, or the user's own handle if they dragged one. Every color is fitted to 3:1 on the theme's cards (`singerColors.ts`, Len's yellow darkened on Daylight, not dropped), the source line adds "colors by you" once a word or voice has a singer, and a song with no coding looks as before. A colored row draws its coding's words as they are (`coded` rows): after "Make second voice" the line keeps its text, which is how it's matched, but its words don't have the echo, so the echo is sung once, under it. Only timed lines move a song's times (`colorLyrics`): a line nobody timed keeps the lyrics' own time (auto-sync's, LRCLIB's) with the coding's words placed on it by their letters and its second voices moved along, and plain lyrics stay plain, colored line by line (and auto-sync still times them), until every line is timed; made-up times never stand in for auto-sync's. Lines the shown lyrics changed under it stay uncoded (matched by exact text, LCS) and are marked "changed" in the editor. Lines the user added in the editor (a verse the lyrics are missing) show in their place, leaving the lyrics' own lines exactly as they'd be without them: in synced lyrics (and plain lyrics the user has timed through, which turn synced on their own lines alone, as before) at their own start, even while it's a guess (the one exception to "made-up times never stand in": the user placed the line by ear, and nothing else would show it), and in plain lyrics not yet timed through in the coding's order (after the shown line before it; when the lines before it changed in these lyrics, just before the next shown one). While the coding has the lyrics' own line with the same words (a repeated line), an added line never takes its row, only fills in beside it; it gives way only to such a line, never to another added one, so a line the user added twice shows at each of its own times, never twice at one. An added line like an unmatched shown line between the same matched lines (`likeness` ≥ 0.5, `standIns`) stands in for it, its words, singers and times shown in that line's stead, so a verse the lyrics gain on a re-check or another version never shows twice. When none of the lyrics' own lines match, added lines don't show either: an added line matching alone may be another version's verse. The lyrics' own rows ride along as `colors.own`, where auto-sync and the editor read the lyrics' own lines.
- Album colors in the lyrics (`music.albumInk`, off by default; the user's pick on 2026-11-07, "colored as it's sung" with lifted colors, mockups in `.superpowers/brainstorm/`): a round switch in the lyrics box's top-right corner (`AlbumInkSwitch`, the user asked for it in the box itself, not Customize), its dot in the cover's colors while on. Romaji follows its line, quieter; under the light its colors stay put beneath a solid veil of its unsung grey. Untimed lyrics stay in the text color (the user's call), and a song colored by singer keeps its singer colors; the switch hides for both.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- When graphify-out/graph.json exists, run `graphify query "<question>"` before your first grep, search or source-file read for a codebase question, and put this rule in every subagent prompt that explores code. Read raw files only for lines the graph or an earlier read already located. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
- A committed graphify-out/graph.json is rewritten whole on every build, so a large diff to it in a pull request is expected. Do not flag it as churn or suggest skipping the graph rebuild or its hooks.
