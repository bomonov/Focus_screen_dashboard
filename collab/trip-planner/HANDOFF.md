## 2026-11-03 · Codex

**Implemented, uncommitted for Claude's review:** `planTrips` in `raptor.ts`, with `raptorRuns.ts` for service runs/live matching and `raptorLabels.ts` for frontiers and reconstruction. The only change to `raptor.test.ts` is removing `describe.skip`; `types.ts` and other implementation files are untouched. No dependencies or network access added.

**Rounds and range:** A round-based, multi-label RAPTOR range search, one round per exact ride count through `MAX_RIDES`. Each stop keeps a Pareto frontier of arrival time and origin departure, ordered so catching a run uses binary search. Round one seeds every accessible boarding event whose actual origin departure is inside the inclusive window, including the access walk; all window departures are carried together rather than rerunning a single-time search for each one. Later rounds scan only patterns with reachable stops, starting at their first reachable position. Each run keeps its best catchable origin departure as its positions are scanned. Arrive-by uses the same algorithm backwards, with negated clocks and destination arrivals as the range criterion; its seeds must arrive inside that window. This keeps out-of-window journeys out of dominance throughout the search. Completed labels compete across rounds on times and ride count, equal triples collapse, and results are sorted by departure, arrival, then rides.

**Walking and paths:** Only ride-arrival labels expand to one transfer edge, never another walk. Same-stop changes get `MIN_CHANGE_SEC`; footpaths get only their walking duration. Reverse search uses reversed directed footpaths, cached against the timetable. Access/egress always use direct distances from `stopsNear`, independently of footpaths. Immutable parent paths retain run and position indexes; public legs are reconstructed only for surviving answers, with first walks ending at boarding, transfer walks starting at the previous arrival, final walks starting at alighting, and walks under 1 m omitted. Walk-only journeys never enter the search.

**Dates, live times and loops:** Calendar midnights and reverse footpaths are cached in a `WeakMap<Timetable, ...>`. Only actual service runs on window-touched Arizona dates and their preceding dates enter scans, and GTFS times beyond 24:00 stay offsets from their own service midnight. Each live entry is matched against the trip's entire service calendar by its first prediction (departure before arrival at that position), with a strict <12 h cutoff; entries without predictions use the nearest first departure to `query.time`. Cancellation/skips/predictions apply only to that matched run. Each run is scanned independently, so live overtaking does not rely on scheduled trip ordering. Departure and arrival each fall back separately to schedule, scheduled leg fields are retained, and `live` reflects only the boarding departure prediction. Skipped positions cannot board/alight but do not interrupt the ride. Positions, rather than stop ids, control scanning and reconstruction, including repeated stops on loops.

## 2026-11-03 · Codex · Ride chronology follow-up

**Completed, uncommitted:** Both search directions now refuse a ride whose actual alighting arrival precedes its actual boarding departure, using live predictions or each endpoint's timetable fallback. Equality remains valid; only that position pair is refused, so the same run can still supply other valid rides. Documented the rule in `raptor.ts` and the contract in `brief.md`, explained why run pruning preserves exactly the accepted journeys, and added short doc comments to `Path`, `Run`, `Connection` and `Answer`. No edits to `raptor.test.ts` in this round.

**Scanning:** Each run retains a frontier of boarding options ordered by their boarding search time (negated alighting arrival in reverse), using the existing `insert`/`catchable` helpers. Alighting chooses the best option satisfying the ride's chronology. A single best-range option plus a guard would incorrectly lose valid alternatives: a later boarding can have a better origin departure but occur after the live alighting prediction; the earlier boarding must remain available. Reverse search handles the mirrored case with the same frontier. Since accepted rides, changes and walks never move backwards in time, no accepted journey can reach a run wholly before a depart window's start or wholly after an arrive deadline. The bounds include every scheduled and predicted time, retaining boundary equality.

**Regression coverage:** Added 12 focused cases in `raptorRides.test.ts`, covering both modes: timetable boarding/live arrival one second before, equal to, and one second after departure; fallback to a feasible alternative boarding; valid position pairs on a run containing an invalid pair; and an invalid middle ride after a change, with a zero-duration control. Before the implementation, the direct rejection and alternative-boarding cases failed in both modes.
